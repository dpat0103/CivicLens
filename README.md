# CivicLens

**Location intelligence built from normalized public datasets.**

CivicLens turns fragmented government data (Census, BLS, local police,
municipal permits) into a single, readable picture of how a place is
changing: an Area Report with a composite Growth Score, and a
side-by-side Compare view across multiple municipalities.

This is a V1 pilot scoped to **15 New Jersey municipalities** across
five dimensions: housing, employment, safety, transportation, and
population, with 5 years of history (2021-2025).

## Project status: active development

This is not a finished product. It's a working end-to-end pilot with
one real data source wired in and the rest still simulated, built
this way deliberately: prove the architecture with mocked data first,
then replace mock sources with live ones one at a time.

| Dimension | Source | Status |

| Median Household Income | US Census ACS 5-Year Estimates | **Live** |

## How it's built

```
Government Data Sources (Census, BLS, NJ State Police, municipal permits)
              |
      Ingestion jobs (backend/ingestion/)
              |
      Normalization -> shared FIPS-keyed schema
              |
      PostgreSQL / SQLite  (backend/app/models.py)
              |
      Analytics engine (backend/app/scoring.py)
        - 1/3/5-year % change per metric
        - composite 0-100 Growth Score
              |
       FastAPI REST API (backend/app/)
              |
      Next.js dashboard (frontend/)
```

**Backend:** FastAPI + SQLAlchemy. Runs on SQLite by default (zero
setup); point `DATABASE_URL` at Postgres to swap it in with no code
changes.

**Frontend:** Next.js (App Router) + TypeScript + Tailwind + Recharts.

**Data:** This repo ships with a seeded, realistic sample dataset
(`backend/ingestion/seed_data.py`) as a working baseline. Real
ingestion jobs (`fetch_census.py`, `fetch_bls.py`) progressively
replace the mock values with live figures — see the status table
above for what's currently live vs. still simulated.

## Quickstart

### 1. Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# Seed the pilot dataset (15 NJ municipalities x 5 years)
python -m ingestion.seed_data

# Run the API
uvicorn app.main:app --reload --port 8000
```

The API is now running at `http://localhost:8000`. Interactive docs
(auto-generated by FastAPI) are at `http://localhost:8000/docs`.

Quick check:

```bash
curl http://localhost:8000/locations
curl http://localhost:8000/locations/3436000/report
curl "http://localhost:8000/compare?fips=3436000&fips=3432250"
```

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
cp .env.local.example .env.local   # points at http://localhost:8000 by default
npm run dev
```

Open `http://localhost:3000`.

That's it — search a city, view its Area Report, or compare several
side by side.

## The data model

Metrics are stored in a **long/tall format** rather than one column
per metric:

```
metrics(location_id, category, metric_key, label, unit, value, period, source, source_url)
```

This is the deliberate choice that makes the "10+ heterogeneous
government datasets" story work: adding a new metric or a new source
is an INSERT, not a schema migration. Every location is keyed by a
canonical **FIPS code**, which is what Census, BLS, and (via a
ZIP-to-FIPS crosswalk) most municipal open-data portals key off of
natively.

## The Growth Score

A 0-100 composite computed from each location's 3-year % change across
six weighted metrics (population, employment, new housing permits,
median household income, property crime, violent crime — crime is
inverted, since a decrease is the positive direction). The weights and
saturation logic live in `backend/app/scoring.py` and are intentionally
simple and documented so they're easy to explain, defend, or retune.

## Using real data

The seeded dataset is representative sample data, not live pulls — it
exists so the app is immediately runnable with zero setup. To start
replacing it with real figures:

1. Get a free Census API key: https://api.census.gov/data/key_signup.html
2. Get a free BLS API key: https://data.bls.gov/registrationEngine/
3. `$env:CENSUS_API_KEY = "..."` and run `python -m ingestion.fetch_census --year 2023 --state 34`
   (ACS 5-year estimates lag by 1-2 years, so use the most recent
   published year, not the current year)
4. `$env:BLS_API_KEY = "..."` and run `python -m ingestion.fetch_bls --fips <fips> --series <series_id> --start-year 2021 --end-year 2025`

Both jobs upsert into the same `metrics` table the seed script uses, so
real and sample data slot into the exact same schema.

**Note on geographic matching:** the seeded Locations start with
placeholder FIPS codes. `fetch_census.py` matches incoming Census rows
to our Locations by name (not FIPS) and backfills the real FIPS code
on first match — this also required a two-pass fallback, since a
handful of NJ townships (Montclair among them) are classified by the
Census Bureau as "county subdivisions" rather than "places" and don't
appear in the primary place-level query at all. Real government data
disagreeing on categories like this is exactly the kind of mess the
normalization layer exists to handle.

Crime and transportation ingestion jobs (NJ State Police UCR-SRS, NJ
Transit Open Data, municipal Socrata portals) aren't built yet —
they're the natural next ingestion jobs to add, following the same
pattern.
